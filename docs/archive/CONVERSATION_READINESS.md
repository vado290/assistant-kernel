# 0.30.2 对话入口与本轮闭环边界

2026-10-11。本轮优先保证现有主干可用，后续业务调整另行迭代；不恢复 n8n 定时功能，不增加新的定时系统。

## 本轮修复

- Discord 专用 Supervisor 频道及其 Thread 的 `/whoami`、`/binding` 使用实际接口登记，不再因为 PM 绑定表中没有该频道而误报未绑定。
- Supervisor 频道执行 `/pm` 给出本 Project 的 PM 频道，不声称改变当前频道角色。
- 已登记 Supervisor 入口不能被普通 `/bind_project`、`/unbind_project` 命令覆盖；不更改已有归属。
- `/new` 明确说明旧任务和待答保留，避免把切换对话窗口理解为取消任务。

数据库结构、已有角色包、审批与业务执行规则保持兼容。修复只涉及公共入口适配器，不重写固定的 Role/Skill 包，不切换旧任务协议。

## 当前四个入口

顶层 `#kernel` 是管理入口；上表是两个 PROJECT 分类下的业务角色入口。

1. 在四个频道分别发送 `/whoami`，核对 Project 和 Agent。该命令不调用模型、不回答问题、不推进 Task。
2. 在 Supervisor 中发送“只做对话测试：请说明你所属的项目和职责，不执行任务、不修改文件、不把这条消息作为旧问题的答案。”核对模型回复。
3. PM 保留直接入口，但按既定设计，正式工作需要 Supervisor 澄清、具体 Prompt 确认和交接；一次普通消息不代表已经批准执行。
4. trading-risk-bot 仍有旧 `waiting_user` 任务。先用命令检测 PM 通道；普通文字可能作为旧问题答案，不用随意的测试文字回答旧卡。`/new` 只切断旧会话自动答题关联，不能据此认为旧工程主线已关闭。需要处理旧任务时用 `/pending`、`/resume` 和具体用户决定。

## 证据与限制

升级证据目录：`assistant-data/upgrades/kernel-v12-20261008/evidence/`。

- `conversation-readiness.json`：Discord API 只读核对四个真实频道、v1.2 配置可读、旧待答状态与近期队列；未发送消息。
- `conversation-model-inputs.json`：四个角色的模型参数、固定角色 Token 预算和登录有效期元数据检查；没有调用模型，不能代替实际模型成功。
- `conversation-closure-tests.json`：18 项隔离数据库检查，覆盖入口身份、待答保留、Prompt 确认交接、旧问答进入新监督流程；不冒充真人验收。
- `conversation-release-live.json`：新安装包、实际进程版本、服务就绪与受保护状态核对，发布后生成。

此前 P4 实际有限 Python／模型／MCP 证据与 P5 隔离服务工作登记、21→42、停止清理证据继续保留；它们不能证明所有生产业务路径已通过。

## 后续剩余事项

当前支持的基础链为用户输入 → 澄清/问题 → Prompt 确认 → PM 五阶段与 Review → 批准发布/执行 → 结果与状态回写。问答、配置快照、历史引用及独立后台执行保留原机制。

本轮不把以下内容标成完成：完整真实项目业务演示、真人双入口按钮检查、全部有效要求最终逐条接受矩阵、完整跨环境恢复演练。用户已要求压缩验收，不将这些演示作为每次修复的阻塞门槛。

W05 外部消费者仍是部分完成：受管配置渲染、应用组状态和已有消费者回执可用，但 Docling 请求超时尚无对应调用方，独立 Reranker 网关的全部参数应用尚未接通。不能误把该网关参数直接作用于 Kernel 的云端 Qwen 调用，也不能为了补回执启动停用服务。两者不处于当前 Discord → Supervisor/PM 对话链。

后续先根据四个入口的实际反馈修复确定性问题，再补完整业务演示。定时器和实际 Ubuntu 搬迁依照既有批准留待后续，基础版本不因此增加新平台。
