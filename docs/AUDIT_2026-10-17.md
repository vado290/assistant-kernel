# 全系统业务逻辑审计（2026-10-17，基于 0.42.0 / 7715fb7）

范围：任务状态机、调度器、卡片与网关、各执行器（PM / Supervisor / 分诊 / 验证发布 / 创建项目 / 作业）、
MCP 工具服务、代码交付、作业运行时、授权、技能与文档草稿、迭代流水、项目创建与路由。
方法：先画主干，再逐条链路读最新源码；可疑点在 test venv 里做了小探针（未改任何代码）。

## 1. 主干地图

```
Discord ──gateway(_pump 2s)──► kernel.receive ──► machine.user_input
   ▲                                │  空闲项目 → triage run → 答复 / 建任务 / 转交其他项目(_route)
   │                                │  有任务   → 消息挂到当前任务（PM 下一轮读取）或 review_input
   │                                ▼
   │      core.tasks（每项目一个活动任务，P7 游标）── core.runs（单 SQL 领取，租约+心跳）
   │                                ▼
   │      dispatcher.serve：维护节拍（恢复租约、周复盘、vault 同步、作业同步/调度/服务检查）+ claim_and_start
   │                                ▼
   │      执行器：pm_turn → supervisor(evaluate) → 卡片 → 用户点按 → machine.act → 下一个 run
   │               build：候选文件（文件交付）或任务 worktree（代码交付）→ validation → 发布卡 → publish
   │               bootstrap：vault + 频道 + 路由 + 章程 directories 授权
   │               job：script / agent / service_restart
   │                                ▼
   │      close()：撤回卡片项 → 通知 → record_task（core.iterations）→ activate_next
   └──── outbox(core.messages pending) ◄── notify / 卡片同步
```

核对后无问题的关键约束：单 SQL 领取；每项目一个活动任务；审批绑定文档 sha；工具每次调用都查租约；
Supervisor 的 `_grant` 等 Kernel 事实最后合并，模型输出无法伪造；发布不盲目重试（转对账）；
验证/发布前重新封存候选文件并比对 sha；创建项目前检查 project_id 是否已存在；bootstrap 可重复执行；
周复盘的改进方案必须经用户卡片确认才会实施；`InvalidResult` 统一转为可重试失败。

## 2. 发现的问题（按严重程度）

### 高

**H1 调度器维护节拍任一步骤持续出错 → 全系统停止领取任何 run**（已用探针确认）
- 位置：`core/dispatch.py` `serve()`。维护步骤和 `claim_and_start()` 在同一个 try 里，`next_recovery` 只在全部步骤成功后才推进。
- 场景：`check_services` 里 supervisorctl 超时（120 秒抛 `TimeoutExpired`）、`schedule_jobs` 遇到数据库错误、
  `recover_expired` 经 `on_exhausted` 撞上状态机里的确定性 bug（见 M1）、`schedule_evolution` 出错……任一持续出现，
  循环就每秒重试维护、永远走不到领取。所有项目的 PM/Supervisor 都不再响应，只有日志里的 "dispatcher loop error"。
- 探针：让 `recover_expired` 持续抛错，0.5 秒内维护被调用 49 次，领取 0 次。
- 最小修复：维护部分单独 try/except（最好每一步各自 try，记日志后继续），进入维护时先把 `next_recovery` 推到下一个周期；
  `claim_and_start()` 放在维护之外。约 10 行，只动 `serve()`。
- 原由：维护是辅助功能，领取 run 是主干；辅助功能出错不应拖垮主干。

### 中

**M1 状态机处理结果时出现非 InvalidResult 异常 → run 卡 15 分钟后被重新执行，重复耗费模型回合**
- 位置：`core/kernel.py` `complete()` 只捕获 `machine.InvalidResult`；`dispatch._execute` 只捕获 `LeaseLost`。
- 场景：`on_result` 里任何意外异常（KeyError、StaleItem、ValueError 子类以外的 bug）使整个事务回滚，run 仍是 running，
  异常只作为 "Task exception was never retrieved" 记录。15 分钟后租约过期 → 重新排队 → 模型回合整轮重跑 → 同一个 bug 再次出现，
  直到用尽次数；最后 `on_exhausted` 若也触发同一 bug，会在 `recover_expired` 里抛出，进而触发 H1。
- 最小修复：`complete()` 的 savepoint 里加 `except Exception`：记录日志并 `_fail(..., {"type": "kernel_error"}, retryable=False)`，
  让用户立刻看到"运行失败"卡片，而不是悄悄重跑。
- 原由：结果已经拿到，重跑模型不能修复 Kernel 自身的错误，只会浪费并拖延。

**M2 网关 outbox 队头阻塞**（潜在；生产当前 0 条待发）
- 位置：`gateway/service.py` `deliver_outbox()` 每次只取最早的 20 条 pending；项目没有频道配置或发送持续抛错时 `continue`，
  消息永远保持 pending。
- 场景：一个项目的路由被删除或频道失效后积累 ≥20 条消息，所有项目的出站消息和卡片通知都发不出去。
- 最小修复：项目无频道配置时直接标记该消息失败（`mark_delivered(ok=False)`）；发送抛错且消息已超过例如 30 分钟时标记失败。
- 原由：一条坏消息不应阻塞其他项目；失败状态可查，不会丢失记录。

**M3 目录授权的 key 冲突**（已用探针确认）
- 位置：`core/grants.py` `check_directory()` 用目录名作 key；`machine.grant_directory()` 撤销同 key 的现有授权。
- 场景 a：目录名为 `project` / `candidate`（探针：`H:\AI\project` → key `project`）与工作区的内部根同名 →
  快照出现重复 key，该项目之后所有需要工具的模型调用都失败（或外部目录顶替了项目自己的 vault 根），项目瘫痪直到 `/grants revoke`。
- 场景 b：`a/crypto` 与 `b/crypto` 都得到 `crypto`，批准第二个时第一个被静默撤销。
- 最小修复：`check_directory` 对保留名（project、candidate、run-work 等）加前缀，例如 `dir-project`；
  `grant_directory` 发现同 key 的现有授权路径不同时，在 key 后附加路径短哈希（再计算 policy）。同路径仍按"替换"处理。
- 原由：两处各几行，不改变授权模型；避免一次正常授权让项目瘫痪或让旧授权静默消失。

**M4 验证/发布/创建期间在 PM 频道发的补充消息，在任务结束时丢失**
- 位置：`machine.user_input` 把消息挂到当前任务；`close()` 不处理未消费的消息。
- 场景：任务处于 validating / publishing / bootstrapping 时用户补充"顺便把 X 也改一下"，随后发布成功、任务关闭——
  这条消息既没被 PM 读到，也没有任何回复。
- 最小修复：`close()` 查询该任务未被消费的入站 PM 消息，有则发一条系统通知列出它们（"任务结束前的这些补充没有处理，
  需要的话请重新发送"）；或者把最后一条交给分诊。推荐前者，最简单。
- 原由：静默丢失用户输入是体验上最伤信任的问题之一，而修复只需在关闭路径加一次查询和通知。

**M5 jobs.yaml 可绕过发布审批直接生效；代码交付项目则根本无法通过发布流程修改 jobs.yaml**
- 位置：`executors/pm.py` 的实施回合是 `danger-full-access`，文件交付时 cwd 就是 vault；`jobs.sync_runtime` 每 30 秒读取
  vault 顶层的 `jobs.yaml`，只要 sha 变了就登记作业并写 supervisord 程序。
- 场景：PM 在实施阶段用 shell / apply_patch 直接改了 `jobs.yaml`（而不是写候选文件），30 秒内定时脚本和常驻服务就会
  按新配置运行，没有经过验证和用户批准。代码交付项目里，PM 只能改 worktree，`jobs.yaml` 在仓库之外，只能靠直接写入生效。
- 说明：这是已知限制 A5（实施回合的 shell 写入只靠技能约束）造成的后果中最危险的一个，因为它会自动执行进程。
- 最小修复：发布成功且发布文件包含 `jobs.yaml` 时，记录一条 `runtime_manifest_published` 事件（含 sha）；
  `_sync_project` 只接受发布过的 sha，其他变化忽略，并只通知一次"jobs.yaml 在发布流程之外被修改，已忽略"。
  代码交付项目的 jobs.yaml 放在哪里需要你决定（见第 3 节）。
- 原由：不需要解决整个 A5，只把会自动执行进程的这一条入口收紧。

### 低

**L1 空闲时连发两条消息会产生两个并行的分诊，可能各自建任务**
- 最小修复：`_triage_result` 处理"建任务"时，若项目已有活动任务，就把消息作为补充挂到该任务，而不是新建。

**L2 对账后发布成功时，PM 的迭代记录被忽略**
- 位置：`record_task` 只在 `reason == "published"` 时使用 PM 写的记录；`published_after_reconcile` 走兜底（`complete=false`）。
- 最小修复：两种 reason 都接受。一行。

**L3 发布或创建期间取消任务，副作用保留但任务显示已取消**
- 最小修复：`cancel_task` 在 state 为 publishing / bootstrapping 时拒绝，并回复"正在发布，完成后再取消"。

**L4 `_route` 给目标项目入队咨询时没有锁目标项目**
- 最小修复：按 project_id 顺序锁住两个项目再入队（避免死锁）。实际冲突概率很低。

**L5 按钮或弹窗处理中出现意外异常时，用户只看到一直"思考中"**
- 位置：`discord_app.handle_button` / `CoreModal.on_submit` 在 defer 之后没有异常兜底；例如动作已成功但 `sync_cards` 发送失败。
- 最小修复：包一层 try/except，失败时 followup "处理出错，请看 Supervisor 频道最新卡片"，并记录日志。

**L6 代码交付：主分支在任务期间有了新提交时，发布无法快进，只能人工合并**
- 场景：普通项目一次只有一个任务，影响不大；kernel 项目的主分支经常有开发者直接提交，会经常遇到。
- 最小修复（可选）：快进失败时，Kernel 在任务 worktree 里尝试 `git merge --no-edit <main>`；合并干净就重新封存并验证，
  再出新的发布卡；有冲突就中止合并并按现状报告。

**L7 服务写入 supervisord 失败后不会重试**
- 位置：`_sync_project` 先提交 `manifest_sha`，再调用 `CONTROL.apply`；apply 抛错后下一轮看到 sha 相同就跳过。
- 现状：`check_services` 会报告一次 MISSING，用户能看到，但不会自动恢复。
- 最小修复：apply 失败时把这些服务行的 `manifest_sha` 置空，下一轮自动重试。

## 3. 需要你确认的一处设计

- **代码交付项目的 jobs.yaml 放在哪里**（M5 的后半部分）：
  1. 推荐：放在仓库里，运行时读取主分支上的版本（`git show <main>:jobs.yaml`），随快进发布生效，和代码同一套审批；
  2. 或者：保持在 vault 顶层，代码交付项目改为在发布卡片上单独确认 jobs.yaml 的变化。
