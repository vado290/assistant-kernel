## 2. 变更流水表 `core.iterations`

一行＝一次迭代（一个结束的任务、一次复盘、一次任务之外的变更）。

| 字段 | 内容 | 谁填 |
|---|---|---|
| iteration_id · project_id · task_id | 标识 | 平台 |
| kind | task / review / bootstrap / shared_context / grant | 平台 |
| title | 一句话：做了什么 | PM |
| source · source_ref | 用户 / 复盘（`review:<任务>:P2`）/ 告警 / Supervisor | 平台（来自任务） |
| reason | 为什么改（现象与依据） | PM |
| changes | 改动明细：类型 · 名称或路径 · 增改删 · 说明 · 版本前后 | PM（平台补版本） |
| artifacts | 涉及工件清单（`skill:<名>`、`map`、`charter`、`jobs`、`file:<路径>`…），用于筛选 | 平台 |
| significance | major / minor；迁移、状态机或合同、授权、作业和服务、章程范围或路由、交付方式或能力的变化自动 major | PM ＋ 平台 |
| verification · expected_effect · measure · followups | 验证、预期效果、衡量方法（只能用平台提供的指标）、遗留 | PM |
| outcome · facts | 结果；发布文件、提交、技能版本变化、批准消息 | 平台 |
| effect_status · effect_note · effect_reviewed_in | 效果复核（有效 / 无效 / 待观察） | 复盘后平台回填 |
| complete | PM 的记录缺失或无效时为 false（平台写保底记录，不阻塞发布） | 平台 |
| search_text | 标题、原因、改动说明、工件拼接，预留向量检索 | 平台 |

**产生**：PM 在实施报告"迭代记录"一节写 YAML（合同规定），PM 执行器保存时解析并存入报告元数据，结果显示在文档末尾；
发布成功时状态机在同一事务里写入。没有实施报告的任务（复盘、创建项目、取消、未发布即结束）由平台写记录；
复盘记录来自改进建议（含 YAML 的"上期效果复核"），并回填被复核记录。公共背景修改、授权变化在卡片批准时写入。
每个结束的任务恰好一条记录。

**读取**：复盘默认读近 4 周全部记录（最多 30 条，每条 ≤ 15 行）＋ 6 个月内的 major（每条一行，最多 20 条）；
工具 `list_iterations(days, artifact, major_only, query, limit)` 按需查询；用户命令 `/iterations [天数]`。普通任务不自动加载。

**替代**：停止写 `changes/iterations.md`（已有内容导入后归档）；旧变更台账 `core.project_file_changes` 停止使用、数据保留。
章程去掉"变更记录"一节（已有项目保持原样，新章程背景存档改编为第 8 节）；公共背景不再写"变更记录"。
技能副本修改仍升版本号（模板更新判断依赖它），原因写入流水；公共模板保留 changelog。

## 3. 项目地图

- 文件交付：`knowledge/map.md`；代码交付：仓库内 `docs/MAP.md`（project.yaml `map_path` 可改；kernel 为 `docs/ARCHITECTURE.md`）。
- 固定章节：结构概览 · 组件（用途、关键文件、入口、依赖、相关作业）· 数据与产物位置 · 常见任务从哪里看起。不含变更记录。
- 实施阶段改动结构或组件时 PM 同时更新地图（随交付发布或提交）；地图的修改作为一项记入流水。
- 退役：`get_project_map`、`query_project_map`、`read_map_component`、`refresh_project_map`、`list_project_changes`、`read_change_diff`；
  读取文件时标记地图过期的逻辑；验证器的地图影响检查；目录说明中的旧结构；各项目旧 `knowledge/map/` 归档。

## 4. 复盘技能（运营阶段的核心）

材料：本周运行记录（含按阶段的回合数）＋ 流水（近 4 周、6 个月 major）＋ 用户画像 ＋ 模板更新 ＋ 技能协作断链 ＋（kernel）跨项目概况。
步骤：复核上期效果 → 发现问题（F）→ 归因 → 改进建议（P，含预期效果和衡量方法）→ 考虑过但不建议的 → 需要用户决定的。
子 agent（本周任务 ≥ 3 时）：记录分析、技能与工件审查、反例审查。被采纳的 P 成为带 `ref` 的后续任务，完成后进入流水，下次复核效果。

## 5. 目录授权（A1–A4）

- 创建项目：章程"创建参数"中的 `directories`（路径、read/write、用途），批准章程即授权，项目创建后写入。
- 运行中：Supervisor 决定 `propose_grant`，卡片批准后写入；`/grants` 查看，`/grants revoke <key>` 经确认卡片撤销。
- 校验：路径在 `/home/v/AI` 下且存在；不是其他项目的 vault；不是平台运行目录。下一回合生效。授权变化记入流水。
- 已知限制：实施阶段 shell 的写入不受授权约束，靠技能约束（A5 未做）。

## 6. 技能协作骨架

- 可选 `metadata.io: {reads: [...], writes: [...]}`；复盘材料只列断链（有人写没人读、有人读没人写）。
- 统一正文结构：目的 · 何时用 · 输入 · 做法 · 产出 · 交接 · 自检 · 常见错误（新技能和修改到的技能按此写，不一次性重写）。
- 顺带修正：project-agent 增加代码交付例外；operation 扩充为日常运营；source-scope 改为指向地图文档。
