# Solution Design

读取有效需求 revision/SHA、Project Map、相关实现/配置、近期开变原因、用户决定和必要
运营证据。区分当前实际能力、需要新增的能力和未验证假设；只读核实，不提前实施或激活。

1. 把需求映射到最小可行改动，优先现有 Kernel、Skill、MCP、脚本与服务；避免为小概率
   场景新增编排层、注册平台、常驻 Agent 或复杂恢复引擎。
2. 对确实影响目标的选项比较可行性、成本、复杂度、依赖与限制，给出明确推荐。
3. 形成 `solution-design.v1`：有效需求引用、当前环境与证据、实施步骤、允许改动范围、
   可以并行的任务/写集、测试与验收、运营指标/报告周期、发布激活动作、恢复安排。
4. 标明哪些低风险动作已包含在设计批准中，哪些高影响动作需要最终 diff 和测试证据后
   单独批准；定义严重运营事件的触发条件及已批准安全动作。
5. 缺少会改变方案的用户决定时，提交少量相关问题卡请求。关键问题已有答案或用户批准
   处置后，按 Kernel JSON 合同提交完整设计与设计批准请求。

发现需求实质变化时保存已有设计进展，提交完整需求修订并回 requirements。重新批准后
只重评受影响设计。用户批准设计的具体 revision/SHA 之前，不写 candidate，不注册或
启用新生产任务。来源和事实不完整时明确留待确认，不以推断填充批准范围。
