# Operation

以当前实际运营基线、批准设计中的动作/指标/周期、原始日志和回执为准。服务持续运行
属于后台执行，PM 推理仍在唯一前台主线。空闲运营可无 active_task_id，不能把新工作
静默挂入已完成任务，也不创建平行 PM。

- 核对运行状态和目标指标，区分正常、退化、失败、未知、恢复及数据不足。
- 执行本阶段已明确批准且确实加载的日常 MCP/工具动作，记录效果和回执；不改正式代码
  或临时扩大权限。新增运营规则、能力或调度方案先形成改进提案。
- 收集用户反馈和运行观察，关联来源、发生时间与运营基线；由 Supervisor 判断是当前
  任务补充、下一轮需求还是严重事件，Kernel 负责状态提交。
- 普通事件及需要模型分析的报告排队。确定性采集/报告脚本按既定周期生成事实产物，
  PM 按批准的延迟与升级条件进行解释；不得把尚未分析的报告写成已评估。
- 严重事件依预先批准的运行手册请求安全边界中断，保存事件、当前任务和未结算动作。
  停服务/关闭外部动作等措施必须有具体已有授权；不能凭“严重”临时授权。

形成 `operation-report.v1`：基线引用、报告时间范围、数据来源、目标/指标结果、实际运营
动作与回执、事件与反馈、效果评价、不确定事项及下一步提案。问题与批准仍放入 Kernel
JSON 交互请求，由独立卡片承载，不直接给用户发消息。新需求切入分析后，后台依已有
运营批准继续；Supervisor 故障只暂停 PM 主线，不自动改变后台运行策略。
