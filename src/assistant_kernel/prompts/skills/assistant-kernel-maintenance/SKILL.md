# 维护 kernel 自身

## 基本事实
- 执行你的是当前生产版本的 kernel；你修改的是下一个版本。你的改动在用户部署之前不会影响正在运行的系统。
- 代码仓库根目录的 `AGENTS.md` 和 `docs/ARCHITECTURE.md` 描述了目录结构、核心原则和测试方法，先读它们。
  改了架构或原则，就同步修改这两份文档。
- 不得修改生产环境的虚拟环境、配置、数据库，也不得执行部署脚本。

## PM：设计与实施
1. 设计文档必须说明改动是否影响核心原则（例如"每个活动任务只有一个游标""卡片每个项目一张"），以及如何保证不被破坏。
2. 修改状态机或决定类型时，必须新增或修改对应的场景测试。
3. 修改提示文本或技能时，说明会影响哪些角色、哪些场合，并按 assistant-capability-maintenance 更新版本和变更记录。
4. 数据库迁移只能新增；迁移要能在已有数据上重复执行而不出错。

## Supervisor：评估与发布卡
评估改动风险（是否涉及迁移、状态机、网关、技能），检查测试是否覆盖了改动；发布卡上写明：
提交编号、测试结果、是否包含迁移，以及"合并后需由用户执行部署"。

## PM：复盘时打磨公共模板
kernel 的周度复盘除了本项目的运行记录，还会拿到 Kernel 汇总的"各项目运营汇总"（按各项目的共享级别提供）：
各项目的运行指标、复盘建议、对技能副本的改动及原因。据此判断公共模板（`prompts/skills/` 中的技能、`core/project_template/`）
哪里该改：
- 多个项目对同一技能做了同类修改 → 很可能是模板的问题，建议把改动吸收进模板；
- 某个技能相关的指标普遍偏差（例如需求阶段平均提问轮数多、Review 退回率高）→ 找出话术原因，提出具体的新写法；
- 只有个别项目需要的修改 → 留在该项目，不进模板。
建议中写明证据来自哪些项目、哪些数据。模板改动发布后，各项目在自己的复盘中决定是否采用。
