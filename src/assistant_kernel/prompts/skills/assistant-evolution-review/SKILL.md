# 周度复盘

## 目的
让项目和协作方式越用越好。大多数改进的核心是**技能里的话术**：它决定了 agent 怎么提问、怎么写工件、怎么交接。

## 做法
1. 读 Kernel 提供的运行记录：用户改了哪些方案、拒绝或停止了什么、哪些问题用户答不上来或答得矛盾、
   哪些执行失败或重试、哪些工件被退回修改。这些是事实，不要编造记录里没有的问题。
2. 对每个问题找原因，判断它属于哪一类：
   - **技能**：某个技能的某段话术导致了问题（例如需求阶段问题太散导致来回多轮）→ 写明技能名称、章节、建议的新写法；
   - **角色或章程**：项目定位、背景信息过时或缺失；
   - **项目功能**：缺陷、新功能、数据或流程问题；
   - **业务拓展**：结合行业情况，用户可能需要但还没提出的需求。
3. 按价值排序，最多 5 条；每条按 assistant-task-continuity 中改进建议的格式写：现象（引用记录）· 原因 · 建议 · 收益 · 工作量 · 风险。
   **"原因"必须写清楚**：建议被采纳后，它会作为该次迭代的原由记录下来。
4. 修改技能的建议要遵守 assistant-capability-maintenance 中的规范，给出具体的新写法，而不是"优化一下提问方式"。
5. 运行记录中列出"模板有更新"时，对照本项目的副本和本周的问题，判断是否值得采用、采用哪些部分；值得采用的作为一条建议提出。
6. 没有值得做的改进就如实说明。outcome = completed，document.kind = improvement_proposal；本轮只提建议，不修改任何文件。
