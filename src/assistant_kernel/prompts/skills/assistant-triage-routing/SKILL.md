# 分诊与路由

## 目的
用户可能找任何一个角色说任何事。闲聊不应该变成任务，属于别的项目的事应该送到对的地方，新的想法应该先商量再立项。

## 判断顺序
1. **闲聊或一次性问答**（问候、随口一问、能直接回答的问题）→ `chat`：直接回答，不建任务。
2. **本项目的工作**：与本项目章程的用途和范围相符 → `start_task`。目标写成一句话，保留用户原话。
   拿不准用户是想"聊聊"还是"开始做"时，先在回复里确认，不要急着建任务。
3. **属于另一个已有项目**（仅当上下文中提供了"项目名录"，即 Kernel 汇总的各项目章程第 1、5、7 节）：用户的请求与某个项目的用途、别名或典型请求相符，
   且不在它的"不负责"范围内 → `route`：写明目标项目、理由和交接说明（用户原话加你的理解）。匹配不确定时，
   列出一两个候选项目问用户，不要硬选。
4. **需要新项目**（仅当本项目有"项目管理"能力）：没有项目匹配，且这是需要持续执行的新业务 → 先和用户讨论：
   这件事的用途、谁用、是不是已有项目的一部分；用户确认要建时再 `propose_project`。

**属于公共背景的事实**（例如用户说"以后都部署到远程主机 B"）：在 kernel 中按 assistant-shared-context 提出更新；
在其他项目中路由到 kernel，交接说明里写明这是公共背景的更新。

## 交接说明的写法（route）
```
用户原话：……
我的理解：用户想要……（一两句）
已知背景：与本次请求相关的事实
建议目标项目先做：例如先确认……
```
目标项目的 Supervisor 只看得到这段交接说明，所以要写成独立可读的内容。

## 常见错误
- 把"你好""在吗"当成任务。
- 用户只是问某个项目的进度，却建了新任务：问进度属于 chat 或 route。
- 为了路由而路由：本项目就能做的事不要推给别的项目。
